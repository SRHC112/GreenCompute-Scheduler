# 分支与合并规范

**文档编号**：GCS-BRANCH-2026-001　**版本**：V1.0　**日期**：2026-11-12　**状态**：待审批

> 依据《产品项目研发流程规范》七（三）「约定五类分支的用途与合并路径」与八（二）「从 develop 拉 feature 分支，自测通过后提 PR/MR，至少一人 Code Review 后合并」。基线不限定提交类型白名单，本项目统一采用 **Conventional Commits**（`feat:` / `fix:` / `docs:` / `ci:` / `refactor:` / `test:` / `chore:` 等均可）。

## 一、五类分支及用途

| 分支类型 | 命名 | 用途 | 保护要求 |
|---|---|---|---|
| `main` | `main` | 随时可发布的稳定历史；仅接受合并，不直接推送提交 | 禁止 force-push；合并前 CI 必须绿 |
| `develop` | `develop` | 集成分支；feature 的汇入目标，保持最新开发态 | 合并前 CI 必须绿 |
| `feature/*` | `feature/<issue-id>-<short-desc>`（如 `feature/17-model-router`） | 单一功能开发；从 `develop` 拉出 | 至少一人 Code Review 后合并 |
| `release/*` | `release/v<版本号>` | 发布准备：冻结功能、只做修复与文档 | 冻结后只接受 `fix:` 提交 |
| `hotfix/*` | `hotfix/<issue-id>-<short-desc>` | 生产紧急修复；从 `main` 拉出，修复合回 `main` 与 `develop` | 事后必须补 Postmortem 记录 |

历史说明：本仓库第一条提交 `Initial commit` 无类型前缀，系仓库初始化时沿用的惯例，不视为违规；此后提交均为 Conventional Commits 格式。

## 二、合并路径

```
feature/* ──(PR/MR + ≥1 人 CR + CI 绿)──▶ develop ──(冻结+回归)──▶ release/* ──▶ main
                                                        │
hotfix/* ──(紧急修复)──────────────────────────────────▶ main ──▶ 同步回 develop
```

- feature → develop：必须经 PR/MR，至少一人 Code Review，CI 全绿后合并；
- develop → release → main：发布前走基线十（一）上线前检查清单（6 项全满足方可发布，任一缺失顺延）；
- hotfix → main：修复后须同步回 develop，避免修复丢失。

## 三、Code Review 规则

| 项 | 要求 |
|---|---|
| 评审范围 | 所有进入 `develop` / `main` 的 PR/MR；重点：逻辑正确性、测试覆盖、安全（凭据/注入/越权）、文档同步 |
| 评审人配置 | 至少 1 名评审人；涉及安全（`.env`、密钥、网络调用）或核心编排引擎（`gcs/`）时建议 2 名 |
| 合入条件 | CI 全绿 + 评审人批准 + 无未解决讨论 |
| 记录 | PR/MR 编号、评审人、结论留存在平台；重大决策同步登记《差异及处理方式记录》 |

## 四、当前仓库现状与过渡方案（差异登记）

| 项 | 基线要求 | 现状 | 过渡动作 |
|---|---|---|---|
| 分支 | 五类 | 仅 `main` 单分支 | 本文档先行落地规范；补建 `develop` 分支；或按《差异及处理方式记录》A-08 由项目负责人书面批准单分支作为裁剪（基线一（三）允许「相邻阶段合并、角色一人多岗」，但不豁免规范本身） |
| CR 记录 | 所有合并经 CR | 无 PR/MR 记录 | 自下一次合并起执行；历史直接 push 的事实登记于《差异及处理方式记录》 |
| 提交规范 | Conventional Commits | 已符合（`feat:` / `fix(ci):` / `ci:` 均合法） | 维持 |
