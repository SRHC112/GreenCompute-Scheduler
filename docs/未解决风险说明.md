## 1. 已实现修复

### P0 · 全新机器上「一键安装」失败

**问题**：`install.py` 的 `precheck()` 在知识包语法预检里 `import yaml`。全新机器（系统 Python 未装 PyYAML）上该导入失败，并被包成「知识包解析失败」——把「依赖未装」误导成「配置文件写坏」，用户会去改 YAML 而问题其实在依赖。同时 `--check` 的依赖校验排在结构预检之后，用户先看到的是错误方向的提示。

**修复**（`install.py`）：
1. `precheck()` 把两种情况分开：缺 PyYAML → **跳过**知识包语法预检并明确说明；YAML 真坏 → 仍报「知识包解析失败」（校验不放松）。
2. `--check` 分支把 `check_runtime_deps()` 提到 `precheck()` **之前**，缺依赖时第一屏就给 `pip install -r requirements.txt` 指引。
3. 完整安装路径下知识包仍被校验：venv 装好依赖后 `verify_install()` 跑单测，单测加载知识包，等价校验不丢失（只是推迟到依赖就绪之后）。

**验证**：`tests/test_install_order_20261115.py` 3 个用例（缺依赖跳过且不误报 / `--check` 优先报依赖 / YAML 真坏仍拒绝）；真实环境 `python install.py --check` → rc=0、5 条 `[ OK ]`；全量单测 190 个通过。

### P1 · 文档未区分两步

README / `docs/DEPLOY.md` 的安装段落已补充「若系统 Python 没有 PyYAML，先 `pip install -r requirements.txt`；或直接运行 `python install.py`（会自动建 venv 并装依赖）」的说明，与 P0 的代码行为保持一致。

### P2 · 装依赖时被「死代理」拦住（v1.0.2 已实现）

**问题**：目标机环境变量里存在指向**未运行端口**的 `HTTP_PROXY`/`HTTPS_PROXY` 时，`pip` 会继承它，
`pip install -r requirements.txt` 直接以 `ProxyError` / `WinError 10061` 失败；最终报出的
`No matching distribution found for PyYAML` 只是表象。`--check` 不受影响（它只查系统 Python 里已有的
PyYAML，不联网），因此容易出现「预检通过、完整安装失败」的困惑。

**修复**（`install.py::install_deps`）：四级网络自愈 ——
① 默认源；② 清除全部代理变量（大小写两套）直连；③ 追加清华镜像；④ 使用 `vendor/yaml`
（PyYAML 6.0.3 纯 Python 实现）离线降级。每一级降级都打印中文 `[WARN]`，不静默替换；
复制后回读 `import yaml` 校验，失败自动回滚。代理变量只在子进程 `env` 副本中清除。

**验证**：`PIP_NO_INDEX=1`（模拟完全无网）实测 → 三次失败后自动降级 → 190 个用例全绿 →
`run.bat test` / `demo` 均 rc=0；联网正常时首次即成功、无任何警告。

**副产品澄清**：同一机器曾出现「13 errors + 1 failure」，全部为 `No module named 'yaml'`
（依赖未装上的下游后果），**与 Python 3.14 无关**；补装依赖后 190 个用例在 3.14.2 下全绿。

## 2. 仅风险说明（本版本不实现）

以下 4 项经评估**不影响提交与评审**，本版本不做代码改动，仅如实披露。

### R1 · CI 无 macOS job

- **风险描述**：文档把 macOS 列为支持平台，但 CI 矩阵只有 Ubuntu×4 + Windows×1，`install.sh` 从未在真机 macOS 上跑过。
- **潜在影响**：macOS 自带 `/usr/bin/python3` 为 3.9.6 < 3.10。未装 Homebrew Python 时首跑会失败——但 `install.sh` 已实现「按版本择优」并在全不满足时给出 `brew install python@3.12` / python.org 指引，属「需先装 Python」而非「跑不起来」。
- **触发条件**：评审/用户使用 macOS 且未安装 3.10+ Python。
- **发生概率**：低（国内评审以 Windows 为主）。
- **缓解建议**：`bash install.sh --check` 可在任意有 Python 3.10+ 的环境先确认脚本逻辑；如需彻底消除，在 CI matrix 增加 `macos-latest`（会增加 runner 配额消耗）。
- **现状**：`install.sh` 逻辑已有版本择优与中文指引；**未做 macOS 实机验证**。

### R2 · 脚本侧产物未走原子写

- **风险描述**：`gcs/demo.py` 与 `evaluation/run_eval.py` 直接 `write_text` 产物（JSON/HTML），未使用平台侧已有的 `.tmp + os.replace` 原子写。
- **潜在影响**：进程在写盘中途被强杀（Ctrl+C / 断电）时，可能留下半截 JSON，后续读取报解析错，且现场难以区分「产物坏」与「代码坏」。
- **触发条件**：恰在毫秒级写盘窗口内被强制终止。
- **发生概率**：低。两者均为单进程顺序写、无并发竞争；实测 16 线程并发 HTTP、4 进程并发 demo、8 线程同目标写，JSON 解析失败 0、残留 `.tmp` 0、不完整 HTML 0。
- **缓解建议**：产物可由 `python evaluation/run_eval.py` / `python -m gcs.demo` 一条命令重算恢复；若要根治，把 `app/server.py` 的 `_write_atomic` 抽为公共工具供两个脚本复用。
- **现状**：HTTP 侧已原子写；**脚本侧未改**。

### R3 · `runs/` 目录无自动清理

- **风险描述**：每次 `python -m gcs.demo` 新建 `runs/run_<时间戳>_<policy>/`，无保留策略。
- **潜在影响**：长期反复演示后目录持续累积（单次约 20–60 KB）；不影响功能，仅列表变长、占用少量磁盘。
- **触发条件**：必然发生（每次运行），但后果轻微。
- **发生概率**：必然。
- **缓解建议**：演示前手动清理非最新目录即可；提交包已排除 `runs/run_*`（仅保留 `.gitkeep`），不影响交付内容。
- **现状**：**未实现**自动清理（保留历史便于评审现场回看）。

### R4 · CSS 两份重复且已漂移

- **风险描述**：`gcs/report.py` 与 `app/server.py` 各维护一份完整 CSS，两处样式存在细微差异。
- **潜在影响**：同一份看板经不同入口渲染时视觉细节可能不一致；后续若只改一处会继续分叉。
- **触发条件**：仅在再次修改样式时暴露；当前静态状态下无可见故障，两处均正常渲染，浏览器 console error 为 0。
- **发生概率**：中（仅当再次改样式）。
- **缓解建议**：后续把公共样式抽到单一模块（如 `gcs/webassets.py`）再分别引用。
- **现状**：**未合并**，属技术债，不影响评审。

## 3. 澄清：以下现象**不是**缺陷

| 现象 | 结论 |
|---|---|
| `evaluation/results.csv` 使用 CRLF 行尾 | RFC 4180 要求；`.gitattributes` 设 `*.csv -text` 禁止转换，为有意设计 |
| `--port 0` 被接受 | POSIX 惯例；`server.py` help 与实测记录自洽，改严反而不一致 |
| HTTP/0.9 请求无响应头 | 协议强制行为，任何合规服务器均无法发送响应头 |
| 浏览器对非 2xx 记录 network 日志 | 浏览器通用行为（`source=network`），JS 异常为 0；UI 已有中文错误提示 |
| HTTP `jobs` 越界返回 400（而非静默夹紧） | 有意收紧：原夹紧会静默产出全零指标，现改为明确拒绝，已在 CHANGELOG `Changed` 段记录 |
