# 架构说明

一句话：**把「一批算力作业怎么跑」从规则脚本，变成一个七角色、八状态、可定向返工、可复现的多智能体闭环。**

---

## 一、分层与边界

```
┌──────────────── L5 展现层 ─────────────────┐
│  app/server.py  零依赖操作台（四区块）        │
│  gcs/report.py  单文件看板 console.html       │
├──────────────── L4 评测层 ─────────────────┤
│  gcs/verifier.py  五层验证器（L1~L5）          │
│  gcs/reflect.py   六维 rubric + 归因 + 返工    │
│  evaluation/      对照实验与原始数据           │
├──────────────── L3 编排层 ─────────────────┤
│  gcs/orchestrator.py  八状态机 + 定向返工 + 熔断 │
│  gcs/dag.py           DAG 构图 + 并行组 + 返工边 │
├──────────────── L2 智能体层 ────────────────┤
│  gcs/agents.py  A1~A7 七角色 + 角色卡 + 工具白名单 │
│  gcs/llm.py     模型网关（两级路由 + 自定义适配器 + 离线降级）│
├──────────────── L1 领域层 ─────────────────┤
│  knowledge/ningxia_cluster.yaml  知识包（版本化）  │
├──────────────── L0 资源层 ─────────────────┤
│  gcs/simulator.py  算力模拟器（故障注入 + 成本核算） │
└──────────────────────────────────────────┘
```

**边界纪律（答辩最容易被追问的点）：**

1. 模拟器只负责「按计划执行并给出真实结果」，**不含任何调度逻辑**——调度决策全部来自 Agent，
   这是「Agent 智能化而非硬编码」的技术边界。
2. 所有指标数字由确定性模块计算，模型只产出**归因叙述**与**语义层 Judge 意见**，
   避免 LLM 幻觉污染指标。
3. 能用规则判定的缺陷一律不交给模型（L1~L4 全部确定性），模型只在 L5 语义层兜底。

## 二、八状态机

```
PARSE → PLAN → SCHEDULE → EXECUTE → VERIFY ──通过──→ REPORT
                             ↑          │
                             └─ REWORK ←┘（不通过且返工预算未尽）
```

| 状态 | 负责角色 | 关键产出 |
|---|---|---|
| PARSE | A1 | 作业清单、类型分布、需求澄清项（不完整则挂起等人工） |
| PLAN | A2 | 逐作业时长估计 + 置信度 + 方法标注 + 证据 |
| SCHEDULE | A3 | 作业→池→起始时刻 + 目标函数得分 + 对照依据 |
| EXECUTE | A4 | 执行结果与异常（只发现异常，不做判定） |
| VERIFY | A5 | **可归因的缺陷清单**（owner / node / evidence / action） |
| REFLECT | A6 | rubric 六维得分 + 归因 + 定向返工 JSON |
| REWORK | A2/A3 | 只重跑责任子树，保留其余作业原排程 |
| REPORT | A7 | 报告 + 指标表 + 成本碳排归档 |

## 三、DAG 与定向返工

- 节点四类：`TASK` / `DECISION` / `CHECK` / `HUMAN`；
- 关键路径上的 DECISION 与 CHECK 强制串行，保证可解释性不被并行打乱；
- 无数据依赖且预算不冲突的节点进入同一并行组（`Dag.levels()`）；
- 返工边（`reflect → profile / schedule`）标记为 `loop`，**不计入拓扑层级**，
  由编排器在运行时按缺陷的 `node` 字段定向激活。

**定向返工的关键实现细节**：返工时不是整批重排，而是
`plan.update(fresh)` —— 只用责任节点的新方案覆盖旧方案，其余作业的排程原样保留。
若整批重排，未受影响的作业会被重新洗牌，反而引入新的 SLA 违约。

## 四、多目标调度

单次决策在**满足硬约束**的前提下对多个软目标加权最小化：

```
J = w_wait·min(1.5, wait/window)
  + w_cost·(cost/budget)
  + w_green·(1−green)
  + w_carbon·(1−green)
  + w_reliability·congestion
```

- 权重来自知识包 `job_profiles[*].weights`（按作业类型给模板），**代码里没有任何经验常数**；
- 硬约束优先：预计完成时刻超过截止时间的候选直接出局；
  全都不可行时退化为「最早完成」，把迟到压到最小，而不是继续按目标函数挑；
- 候选起点不只是「最早能排在哪」，还会主动对齐**谷段电价起点与峰段终点**——
  这正是电价与绿电窗口利用的来源（`_candidate_starts` 的 `full` 模式）；
- 每条决策附带对照依据（`_rationale`）：选定什么、因为什么排除了更便宜/更绿的候选。

> 宁夏以光伏为主：**正午绿电最好，同时也是峰电价**——成本与绿电在这里是真实冲突，
> 不能靠「都选最好的」蒙混过关。这正是多目标调度存在的理由。

## 五、五层验证器

| 层 | 内容 | 依赖模型 |
|---|---|---|
| L1 结构 | schema、字段齐全与类型 | 否 |
| L2 数值 | 可复算、单位口径一致（成本公式复算） | 否 |
| L3 约束 | SLA / 成本 / 资源 / 绿电 | 否 |
| L4 可达性 | 引用与依据快照存在、依据非空 | 否 |
| L5 语义 | 结论与依据是否匹配 | 是（离线退化为规则） |

输出的不是「通过 / 不通过」，而是**缺陷清单**，每条带：
`code / layer / owner / node / detail / evidence / action`。
这是「定向返工」能只退一个节点的前提。

## 六、自省闭环

- 六维 rubric：硬约束 30 / 数值一致性 20 / 证据强度 20 / 任务覆盖度 15 / 结构合规 10 / 成本效率 5，
  通过阈值 80；
- 缺陷归因区分「估错了」与「排错了」：
  实际时长 / 估计时长 > 1.2 判为估错（退 A2 重估），
  否则判为排错（退 A3 重排）——两者的修复动作完全不同；
- 返工预算：`max_rounds=2`、`max_tokens=600000`、`max_seconds=900`，超限升级人工并保留现场；
- **失败即资产**：实测超时比例写回画像经验库（`Profiler.learn`），
  下一轮估计自动按历史校准，系统越用越准。

## 七、可复现性

| 环节 | 做法 |
|---|---|
| 作业流 | 由 `(seed, 作业序号)` 决定，同种子必得同一批作业与同一批故障真值 |
| 故障真值 | 返工不可见——Agent 不能通过「改真值」来通过验证 |
| 知识包 | 版本号 + 指纹（fingerprint），改动必须升版本 |
| 评测 | 六组共用同一份数据与同一份评测脚本（G-A/G-B/G-C/G-D/G-E1/G-E2），仅切换 `Policy` 开关 |
| 原始数据 | 逐次落 `evaluation/results.csv`，方案书每个数字都能追溯到行 |
