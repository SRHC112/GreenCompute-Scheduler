## 三、旁白逐字稿（可直接照读）

> **口径提示（不读入旁白）**：本稿出现两组 rubric 数字，对应不同对象，均经实测核对，不得互换或叠加——①【单次 demo 运行】`gcs.demo --jobs 60 --seed 20261111` 的 `artifact.json`：首轮 70 分 → 返工 2 轮后 **100 分**；②【六组统计评测】`evaluation/summary.json`：G-A 基线 **70** → G-D 本方案 **90**（三个种子均值）。录制时按镜头所属对象引用，勿混用。

> 说明：`｜` 表示换气停顿，`**粗体**` 为必须念准的数字。

**【00:00-00:12 封面】**

绿算调度，一个面向东数西算宁夏枢纽的算力作业多智能体编排平台。｜本视频用三分半，完整演示它的编排、调度、验证与反馈闭环。

**【00:12-00:35 问题陈述】**

先看问题。｜算力枢纽的难点不在于算得快，而在于**什么时候算、用哪张卡算、算错了谁来兜底**。｜风光电出力随时波动，PUE 与电价随之上蹿下跳；而现有 Agent 框架大多停留在脚本化流水线，调度靠先来先服务，结果没有自动校验。｜我们针对的正是这三件事：编排、调度、验证。

**【00:35-01:05 平台界面】**

这是平台的本地操作台，一条命令启动，不依赖任何第三方服务。｜界面分四块：任务发起，用自然语言描述一批作业；DAG 拓扑，把任务拆成有依赖的图；运行轨迹，记录每个 Agent 的动作；评测看板，直接读评测结果。｜四块对应官方要求的四个环节，我们逐块看。

**【01:05-01:50 Agent 编排】**

编排层我们定义了**七个角色**：需求解析、知识检索、调度规划、执行、验证、返工、报告。｜每个角色有自己的角色卡、工具白名单和失败出口——失败出口这点很关键，它让错误不会无声地传下去。｜角色之间不是自由对话，而是走一张 DAG 和一套**八状态机**：待命、就绪、执行、校验、返工、通过、阻塞、终止。｜看这张拓扑图，并行的分支同时跑，条件不满足时走回退边，而不是整条流水线重来。｜这套编排是代码化的，可版本管理、可复现，不是拖拽出来的黑盒。

**【01:50-02:35 任务调度执行】**

现在跑一次完整编排：六十个作业，固定随机种子。｜终端输出四个关键指标：SLA 达成率 **100%**，单位成本 **2.60 元每 GPU 小时**，平均绿电占比 **71.5%**，碳排 **55.1 公斤**；返工 **2 轮**，rubric 满分 **100**。｜注意，同样的种子和参数必然得到同样的数字，这是可复现的前提。｜打开看板，左边是作业在时间轴上的排布，右边是每一步的指标变化。｜调度器在做的，是在时延、成本、绿电之间找一个可解释的折中，而不是单一目标最优。

**【02:35-03:05 结果验证与反馈闭环】**

验证是我们花力气最多的地方。｜五层验证器：结构校验、约束校验、数值复算、交叉比对、rubric 评分。原则只有一句：**能用规则判定的，绝不交给模型判定**。｜校验不通过会触发定向返工——只重跑出问题的那一段，而不是整体重来。｜这里可以看到返工记录：哪条缺陷、归因到哪个角色、第几轮修复。｜一次典型运行里，rubric 从 **70** 分被拉到 **100** 分，靠的就是这个执行、验证、修正的闭环。

**【03:05-03:35 量化对照】**

增量到底来自哪里，我们做了**六组对照**，每组三个种子、八十个作业。｜和先来先服务相比：单位成本降 **15.1%**，碳排降 **11.6%**，rubric 从 **70** 提到 **90**。｜代价是 SLA 从 100% 降到 **99.2%**——我们选择把这个权衡如实放出来，因为评审需要的是可信的数字，不是好看的数字。｜消融实验也说明，去掉自省闭环后 rubric 直接掉回 70。

**【03:35-03:55 收尾】**

代码全部开源，Apache-2.0，零第三方运行时依赖，一条命令完成环境检查与安装。｜绿算调度，让每一度绿电用在正确的时间、正确的卡上。谢谢。
