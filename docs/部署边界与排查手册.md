# 部署边界与排查手册

> 版本：v1.0（2026-11-15）　适用代码：技术方案 V0.3 / 代码 tag `v1.0.1`
> 定位：记录**已知但未修复**的三类部署姿态问题（半开连接、鉴权 `off` 模式、安装脚本外部依赖），
> 给出可直接照做的排查与处置步骤。**不改代码**，只提供判断依据与备选方案。

---

## 一、适用范围

**该看这份文档的场景**：

1. 把操作台从 `127.0.0.1` 换到 `0.0.0.0` / 局域网 IP / 反向代理后面，准备对外演示或试用；
2. 现场出现「服务打不开」「一直转圈」「大量 503」，但进程还活着；
3. 有人反馈「没登录也能跑任务」「运行记录被外人看到了」；
4. 换机器重装后怀疑「装的不是同一版代码 / 依赖版本不对」；
5. 准备把仓库公开、或让第三方执行 `install.py`。

**不适用**：功能性缺陷（编排、指标、返工逻辑）请看 `docs/测试报告.md` 与 `docs/回滚预案.md`；
鉴权怎么配、Token 怎么轮换请看 `docs/DEPLOY.md` 与 `README.md` 3.5 节。

**三条结论先给**：

| 问题 | 一句话结论 | 默认配置下会不会遇到 |
|---|---|---|
| 半开连接 | 只影响可用性：64 条慢连接可让服务**全拒 60 秒**，不崩溃、不越权 | 不会（只在本机回环时别人连不进来） |
| `off` 模式 | 匿名可**读写**全部接口，包括触发编排 | 不会（默认 `loopback`，对外一律 401） |
| 安装脚本 | `clone` 取 HEAD、`pip` 不校验哈希，属供应链风险，非代码漏洞 | 会（只要执行 `install.py` 装依赖） |

## 二、快速索引（对症找章节）

| 你看到的现象 | 大概率原因 | 跳到 |
|---|---|---|
| 页面打不开、接口大量 `503`，几十秒后自己恢复 | 半开/慢速连接占满 64 个并发槽，等 `timeout=60` 释放 | 第四节 |
| 进程还在、端口在听，但请求一律超时或断开 | 同上（连接被信号量拒绝后立即关闭） | 第四节 |
| 没带 Token 也能 `POST /api/run` | `GCS_AUTH_MODE=off`，或 `loopback` 且从本机访问 | 第五节 |
| 启动横幅里有 `WARN GCS_AUTH_MODE=off` | 同上，属于「故障回退」模式被当默认用了 | 第五节 |
| 同事重装后指标/行为与你不一致 | `clone` 取的是 HEAD，两次装的可能不是同一版 | 第六节 |
| 双击 `install.bat` 报「不是内部或外部命令」或乱码 | 批处理被改成 LF 或含非 ASCII 字节，cmd 解析错行 | 见下「附：Windows 批处理约定」 |
| 担心「装的 PyYAML 被人换过」 | `pip` 未启用哈希校验 | 第六节 |

## 三、排查前置：先确认「当前是什么姿态」

任何一条问题，先跑这三个命令，把「绑定地址 / 鉴权模式 / 依赖版本」固定下来，再谈现象：

```bash
# 1) 监听在哪个地址、哪个进程
#    Windows
powershell -NoProfile -Command "Get-NetTCPConnection -LocalPort 8000 -State Listen | Select-Object LocalAddress,OwningProcess"
#    macOS / Linux
lsof -nP -iTCP:8000 -sTCP:LISTEN

# 2) 鉴权模式与凭据状态（不打印明文）
python app/auth_tool.py status

# 3) 依赖与版本
python -c "import sys, yaml; print(sys.version.split()[0], yaml.__version__)"
```

判读要点：

- `LocalAddress` 是 `127.0.0.1` / `::1` → 只有本机能访问，**问题 4、5 基本不可能触发**；
- 是 `0.0.0.0` / `::` / 局域网 IP → 同网段可访问，问题 4、5 都进入「可触发」区间；
- `auth_tool status` 显示 `off` → 直接看第五节；显示 `loopback` → 本机免凭据、非回环 401；
- `GCS_STRICT_AUTH=1` 时只允许 `required`，`off` / `loopback` 会在启动阶段被拒绝（fail-closed）。

## 四、问题一：半开连接导致服务短时全拒（P3-4）

### 4.1 现象

- 浏览器一直转圈或直接报「连接被重置」；`curl` 返回 `503` 或立刻断开；
- 服务进程仍在、端口仍在监听、CPU 不高；
- **约 60 秒后自动恢复**，无需重启；
- 服务端 stderr 能看到若干 `503`，但没有异常堆栈。

### 4.2 实测数据（2026-11-15，本机回环）

| 条件 | 结果 |
|---|---|
| 正常请求 | `200`，耗时 0.04 s |
| 打满 64 条「声明 `Content-Length: 100` 只发 2 字节」的连接后 | 新请求 `503` 或 `ConnectionAborted`，**请求不被处理但也不挂死** |
| 恢复时间（`timeout=60`） | **60.1 s** |
| 恢复时间（把超时改成 10 s 的对照版本） | **10.1 s** |
| 线程数 / 内存 | 被信号量封顶，不随连接数增长；无残留进程 |

### 4.3 产生原因

1. 服务是 `ThreadingHTTPServer` + `BoundedSemaphore(64)`：每条连接占一个线程，超过 64 条直接回 `503` 并关闭（**这是有意的 fail-fast**，避免线程被打爆）；
2. 请求体是**阻塞式**读取：`rfile.read(Content-Length)` 会一直等到字节凑齐或 socket 超时；
3. `Handler.timeout = 60` 决定了这条连接最多占用线程 60 秒；64 条同时卡住 → 60 秒内没有可用槽位；
4. 判定点在**读完请求行/头之后**，所以「发一半正文」比「完全不发」更高效地占住线程。

### 4.4 影响面

- **不影响**：数据完整性、鉴权、指标计算、进程稳定性；服务不会崩溃，也不需要人工重启；
- **影响**：60 秒量级的可用性中断。若恰好发生在答辩演示，表现为「页面打不开」；
- **不可远程利用的部分**：必须有网络可达性；且攻击者只能造成短时拒绝，拿不到任何数据或权限。

### 4.5 排查步骤

```bash
# 1) 看是否被 503 刷屏（服务端 stderr）
#    出现 "[SEC]" 之外的 503 记录、且时间集中在几十秒内 → 疑似被占满

# 2) 看连接数与状态（Windows）
powershell -NoProfile -Command "Get-NetTCPConnection -LocalPort 8000 | Group-Object State | Select-Object Name,Count"

# 3) 直接探测一次，看是「拒绝」还是「挂起」
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" --max-time 3 http://127.0.0.1:8000/api/policies
#    503 / 0.00x  → 并发槽已满（问题 4）
#    000 / 3.00x  → 连接建立但无响应，或超时
```

### 4.6 解决方案（三档，按暴露面选）

| 方案 | 做法 | 效果 | 代价 / 影响 |
|---|---|---|---|
| A. 前置反向代理（推荐对外） | nginx：`client_header_timeout 5s; client_body_timeout 5s; limit_conn`，并只反代到 `127.0.0.1:8000` | 从源头掐断慢连接，效果最彻底 | 需要运维；不改代码；评审机器上通常没有反代 |
| B. 降低读超时（1 行） | `Handler.timeout = 60` → `10`（实测恢复窗口 60.1 s → 10.1 s） | 暴露窗口缩小 6 倍 | 极慢客户端会被断；本项目请求体只有几十字节 JSON，实际影响≈0；**改的是已验证基线，需重跑回归** |
| C. 分块读 + 每块截止时间 | 按块读请求体，超过累计时限即断开 | 语义最精确 | 代码复杂度上升，收益与 B 相同，性价比低 |

**不要做的事**：把并发上限调大（只是把 60 秒的坑挖大）、去掉信号量（等于放弃 fail-fast）。

### 4.7 验证是否修好/缓解

复现脚本骨架（本机回环即可，无需外部工具）：

```python
import socket, time, http.client
socks = []
for _ in range(64):                      # 与 max_concurrency 对齐
    s = socket.create_connection(("127.0.0.1", 8000), timeout=3)
    s.sendall(b"POST /api/run HTTP/1.1\r\nHost: 127.0.0.1:8000\r\n"
              b"Content-Type: application/json\r\nContent-Length: 100\r\n\r\n{}")
    socks.append(s)
c = http.client.HTTPConnection("127.0.0.1", 8000, timeout=2)
c.request("GET", "/api/policies"); print(c.getresponse().status)   # 预期 503
```

恢复时间测量：打满后每 1 s 探测一次，记录首次回到 `200` 的时间。方案 B 应落在 ~10 s 量级。

### 4.8 注意事项

- 该问题**只在「端口对不可信网络可达」时有意义**；本机回环演示可不管；
- 服务是 HTTP/1.0 无 keep-alive（既有行为），空连接不会长期驻留，60 秒是上限而非永久；
- 若你看到的是「服务直接退出」，那不是这个问题，去看 `docs/DEPLOY.md` 的端口占用与鉴权 fail-closed 章节。

## 五、问题二：`off` 模式下局域网匿名可写（P3-5）

### 5.1 现象

- 同一网段的另一台机器，不带任何凭据即可 `POST /api/run` 并拿到 `run_id`；
- 也能读 `/api/run/<rid>`、`/console/<rid>`（含运行轨迹、LLM token 用量、内部路径）；
- 服务启动横幅里有 `WARN GCS_AUTH_MODE=off：所有接口无需凭据，仅限可信本机调试`。

实测（`--host 0.0.0.0` + `GCS_AUTH_MODE=off`，从本机局域网地址 `172.18.208.1` 发起）：

```
POST /api/run => 200 {"run_id": "run_20261115_140104_673197_full", "policy": "G-D 本方案", ...}
```

### 5.2 产生原因

- `AuthConfig.enabled = (mode != "off")`；`check()` 第一行就是 `if not self.enabled: return AuthResult(True, "off")`——**短路放行所有接口**；
- `off` 的定位是「鉴权组件本身出故障时的回退」，不是常规模式；但它在配置里是可选项，且不校验绑定地址；
- 真正的硬约束是 `GCS_STRICT_AUTH=1`：置位后只接受 `required`，`off`/`loopback` **拒绝启动**。它默认不开启；
- 默认模式 `loopback` 是安全的：本机回环免凭据、非回环一律 401。问题只在「显式设 `off` + 绑定非回环」的组合下成立。

### 5.3 影响面

| 影响 | 说明 |
|---|---|
| 算力/额度消耗 | 可反复触发编排；若配置了在线模型（`GCS_LLM_*`），会真实消耗 token 额度 |
| 信息泄露 | `/console/<rid>` 含完整轨迹、工具调用、token 用量、内部路径；`/api/runs` 可枚举历史运行 |
| 磁盘增长 | 每次运行都会在 `runs/` 下落产物，可能被刷满 |
| 审计缺失 | `off` 模式下不产生 401 记录，事后无法从日志追溯「谁跑过」 |

**严重度**：局域网内=中；公网暴露=高。默认配置（`loopback` + 回环绑定）下不可触发。

### 5.4 排查步骤

```bash
# 1) 模式与绑定地址（见第三节）
python app/auth_tool.py status
powershell -NoProfile -Command "Get-NetTCPConnection -LocalPort 8000 -State Listen | Select-Object LocalAddress"

# 2) 从另一台机器验证是否匿名可写（把 IP 换成服务端地址）
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://<服务端IP>:8000/api/run \
  -H "Content-Type: application/json" -d '{"jobs":5,"seed":7,"policy":"full"}'
#    200 → 确认匿名可写（问题 5）
#    401 → 正常，说明处于 loopback/required 且凭据生效

# 3) 环境变量里是否残留 off
python -c "import os; print({k:v for k,v in os.environ.items() if k.startswith('GCS_AUTH') or k=='GCS_STRICT_AUTH'})"
```

### 5.5 解决方案

| 方案 | 做法 | 效果 | 代价 / 影响 |
|---|---|---|---|
| A. 对外一律 `required` + `GCS_STRICT_AUTH=1`（推荐） | 生成凭据后启动；strict 让误配在启动阶段失败 | 彻底消除匿名读写；配置错误不会静默降级 | 需要分发 Token；`off` 的故障回退能力在对外场景被禁用（这是有意的） |
| B. 保持 `off` 但只绑回环 | `--host 127.0.0.1`，用 SSH 隧道/反代暴露 | 0 代码改动，风险面最小 | 局域网多机演示不方便 |
| C. 代码级硬约束（未实施） | `off` 且绑定非回环时拒绝启动（配 `--insecure-bind` 逃生） | 从根上堵死 | 破坏「局域网快速演示」路径；需重跑回归，故本轮未做 |
| D. `off` 下只放行读、写仍要 Token（未实施） | 改 `requires_auth` | 兼顾便利与安全 | 破坏 `off` 作为「故障回退」的语义，反而更难解释 |

### 5.6 验证是否修好

```bash
# 期望：非回环匿名 POST 返回 401，且响应头带 WWW-Authenticate: Bearer
curl -si -X POST http://<服务端IP>:8000/api/run -H "Content-Type: application/json" \
  -d '{"jobs":5,"seed":7,"policy":"full"}' | head -5

# 期望：strict 开启后，off/loopback 直接拒绝启动（退出码 2）
GCS_STRICT_AUTH=1 GCS_AUTH_MODE=off python app/server.py --port 8010; echo "rc=$?"
```

### 5.7 注意事项

- `loopback` 判定基于 `client_address`：**反向代理 / Docker 网桥会把来源改写成回环地址**，导致看起来「本机」而实际是外网——这正是 `GCS_STRICT_AUTH` 存在的原因，对外部署务必开启；
- 轮换凭据用 `python app/auth_tool.py rotate`，旧凭据保留 24 小时窗口，避免换 Token 期间服务不可用；
- 不要把 Token 写进 URL、日志或 `.env` 之外的任何文件。

## 六、问题三：安装脚本拉取 HEAD、且不校验依赖哈希（P3-8）

### 6.1 现象

- `install.py` 在项目目录外运行时，会 `git clone --depth 1 <REPO_URL>` 取**默认分支最新提交**；
- 随后 `pip install -r requirements.txt`，依赖声明是范围约束（`PyYAML>=6.0,<7.0`），**没有 `--require-hashes`**；
- `--run -- <cmd>` 会用 `.venv` 的 Python 执行你传入的任意命令（argv 列表，不经过 shell）。

### 6.2 产生原因

设计取舍：为了「评委机器上一条命令跑起来」，牺牲了可复现性与完整性校验——固定 commit 会让「取最新修复」失效，哈希锁在多平台/多 Python 版本下极易装不上。

### 6.3 影响面

| 风险 | 触发条件 | 后果 |
|---|---|---|
| 上游仓库被篡改 | clone 时仓库 HEAD 已被替换 | 安装阶段执行任意代码（以当前用户权限），且脚本还会写 `.env`、收紧 ACL |
| 依赖被投毒 | PyPI 上同名包/版本被替换 | 同上，且 `pip` 默认不校验哈希 |
| 两次安装不一致 | 不同时间 clone | 「我这儿能跑、你那儿不能跑」；提交包 SHA256SUMS 无法覆盖 pip 产物 |
| `--run` 执行任意命令 | 包装脚本把不可信参数透传给 `--run --` | 以当前用户权限执行；属调用方责任，不是脚本缺陷 |

**说明**：`--run` 用的是 argv 列表、无 `shell=True`，**不存在命令注入**；风险点是「谁有权决定这条命令」。

### 6.4 排查步骤

```bash
# 1) 确认当前装的是哪一版
git -C <项目目录> log -1 --format="%H %ad %s" --date=iso
# 2) 确认依赖实际版本
python -c "import yaml, sys; print(sys.version.split()[0], yaml.__version__)"
python -m pip freeze | grep -i yaml
# 3) 确认 requirements 是否带哈希锁（本仓库当前不带）
grep -n "require-hashes\|--hash=" requirements.txt || echo "无哈希锁（预期）"
```

### 6.5 解决方案

| 方案 | 做法 | 效果 | 代价 / 影响 |
|---|---|---|---|
| A. 固定 commit SHA | `REPO_URL` 后接 `git checkout <sha>`，或直接 `clone` 指定 revision | 可复现、可审计；与提交包 `SHA256SUMS` 呼应 | 更新需手工改常量；不能自动取最新（约 1 行改动，未实施） |
| B. `--require-hashes` + 锁文件 | 生成带哈希的 `requirements.lock` | 防 PyPI 投毒 | Win/mac/Linux × Py3.10–3.13 的 PyYAML 轮子哈希不同，需多份锁；极易「装不上」，与「一条命令」冲突 |
| C. 随包带 wheel 离线装 | 把目标平台的 wheel 放进 `vendor/` | 完全消除 pip 网络 | 包体积增加约 1 MB；仍需匹配 Python 版本/平台 |
| D. 只用 `--check` / 直接跑源码（当前推荐给评审） | 离线评审不装依赖时：`python install.py --check`；已装 PyYAML 的机器直接 `python -m gcs.demo` | 风险面最小 | 需要机器上已有 PyYAML（多数 Python 发行版不带） |

### 6.6 验证是否修好

```bash
# A 方案后：两次 clone 应得到同一 commit
git -C <目录> rev-parse HEAD        # 与预期 SHA 比对
# B 方案后：篡改依赖应被拒
python -m pip install --require-hashes -r requirements.lock   # 哈希不符应报错退出
```

### 6.7 注意事项

- 提交包自带源码与评测产物，**评审场景不必执行 clone 分支**；真正需要联网的只有 `pip install PyYAML` 这一步；
- 若在有内网镜像的环境，优先用镜像 + `--no-index --find-links`，比哈希锁更实用；
- 永远不要在 `sudo` / 管理员 PowerShell 下运行安装脚本——这会把上述风险放大到系统级。

## 六之二、附：Windows 批处理约定（install.bat）

`install.bat` 是 Windows 的**唯一薄入口**（README 第三节写明「双击 install.bat」），它对编码与换行特别敏感：

| 约定 | 原因 | 违反后的现象 |
|---|---|---|
| 必须 **CRLF** 换行 | cmd.exe 按当前控制台代码页解析批处理；LF 行尾在多字节文本后会被当作 DBCS 字节吞掉 | 整行被截断成碎片命令并执行，报 `'cho.' 不是内部或外部命令` |
| 必须 **纯 ASCII** | 中文等多字节字节会与 DBCS 前导字节组合，产生同样的截断 | 同上，或中文提示显示为乱码 |
| 块内（`if (...)`）**不要出现括号** | cmd 的块解析遇括号会错配 | `then was unexpected at this time.`，脚本直接不执行 |
| 结束前 `exit /b %GCS_RC%` | 否则退出码恒为 0 | 自动化 / CI 把失败当成功 |

**因此**：批处理里只保留 ASCII 提示，**所有中文提示由 `install.py` 以 UTF-8 输出**（脚本开头 `chcp.com 65001` + `sys.stdout.reconfigure(encoding="utf-8")` 兜底）；
仓库根的 `.gitattributes` 固定 `*.bat text eol=crlf`、`*.sh text eol=lf`、`*.py text eol=lf`——没有它，Windows 的 `core.autocrlf=true` 会把 `install.sh` 转成 CRLF，Linux/macOS 上 shebang 带 `\r` 报 `bad interpreter`。

**排查动作**：

```bash
# 1) 确认换行与字符集（Windows 批处理必须是 CRLF + ASCII）
python -c "b=open('install.bat','rb').read(); print('CRLF',b.count(b'\r\n'),'non-ascii',sum(1 for x in b if x>127))"
# 2) 在 Windows 上直接跑一次，看是否出现碎片命令
install.bat --check
```

## 七、同类问题的通用判断框架

遇到新的「疑似部署问题」，按这三问定性，再决定要不要改代码：

1. **暴露面**：服务监听在回环，还是 `0.0.0.0`/局域网/公网？反代有没有改写来源地址？
2. **谁能触发**：本机用户、同网段任何人、还是任意互联网用户？需要什么前提（模式、端口、凭据）？
3. **失败后果**：是**可用性**（打不开、变慢）、**机密性**（能读到不该读的）、还是**完整性**（能改/能执行）？

判定表：

| 后果 \ 暴露面 | 仅回环 | 局域网 | 公网 |
|---|---|---|---|
| 仅可用性 | 可忽略 | 记录，必要时缓解 | 必须处理 |
| 机密性 | 低（本机即信任边界） | 中，建议处理 | 高，必须处理 |
| 完整性/执行 | 中（同机多用户场景） | 高，必须处理 | 高，必须处理 |

经验：**「能不能被别人连上」比「漏洞本身多严重」更决定优先级**；本项目的默认姿态（回环 + `loopback`）已经把绝大多数问题挡在门外。
