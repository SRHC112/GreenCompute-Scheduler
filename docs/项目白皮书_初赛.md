## 一、项目概述

### 1.1 项目背景

「东数西算」把算力需求西迁到宁夏中卫—银川枢纽，随之而来的是一个被长期忽视的运营问题：**算力便宜了，但算得对不对、绿不绿、划不划算，没人能算清楚。**

真实的枢纽调度台上有三个矛盾同时存在：

1. **绿电是波动的**：风光出力在一天内大幅起伏，同一个作业放在 10 点跑和放在 14 点跑，碳排可以相差 20% 以上；
2. **预算是硬的**：单位算力成本（元/GPU·h）是运营方唯一的考核线，超了就是亏损；
3. **时延是承诺的**：SLA 一旦写进合同，晚一分钟就是违约。

传统做法靠调度员凭经验拍板：不可解释、不可复现、更不可度量。而市面上通用 Agent 框架擅长「让模型多轮对话把事做完」，却不擅长「在硬约束下做可复核的数值决策」——把调度交给大模型自由发挥，等于把可审计的运营变成不可审计的对话。

### 1.2 应用范围

| 场景 | 说明 |
|---|---|
| 算力枢纽运营 | 训练/推理/批处理混合队列的排程，按绿电窗口、电价分时与 SLA 做多目标折中 |
| 高校与科研机构 | 校内 GPU 集群的作业排队与成本归集，教学演示可直接用模拟器离线跑通 |
| Agent 系统工程教学 | 七角色协作、DAG 状态机、五层验证器的完整可运行样例，作为课程脚手架 |
| 通用可迁移 | 调度目标函数与验证器分层与行业无关，替换知识包即可迁移到其他资源调度场景 |

### 1.3 核心优势

1. **可复现**：同一随机种子与参数必然得到同一组指标，评委可现场用一条命令复算（`python -m gcs.demo --jobs 60 --seed 20261111`）。
2. **零第三方运行时依赖**：只依赖 Python 标准库（`install.py` 仅需 PyYAML 解析知识包），评审机器不会因 pip 失败而开天窗。
3. **可验证而非可解释**：五层验证器用规则判定结果对不对，模型只负责把话说清楚——「能用规则判定的，绝不交给模型判定」。
4. **量化增量**：六组对照实验（含两组消融）证明每一分改善来自哪个模块，而非笼统宣称「AI 提效」。
5. **诚实披露取舍**：主动公布 SLA 由 100% 降至 99.6%、去掉绿电权重后成本更低等不利数字，结论是算出来的，不是挑出来的。

## 二、解决方案

### 2.1 架构设计

平台为六层结构，自下而上：**领域知识层 → Agent 组织层 → 编排层 → 调度层 → 验证与自省层 → 呈现层**。

```
呈现层     本地操作台（四区块）· 单文件 HTML 看板 · Markdown 报告
验证自省层  五层验证器 · 六维 rubric · 定向返工控制器 · 预算熔断
调度层      多目标加权求解 · DAG 优先级 · 绿电窗口对齐 · 资源画像
编排层      八状态机 · DAG 构图 · 断点续跑 · 人工介入
Agent 层    七角色（解析/检索/调度/执行/验证/返工/报告）+ 工具白名单
知识层      领域知识包 nx-2026.12（电价分时 · 风光窗口 · PUE · 机型功耗）
```

关键设计取舍：**编排不是 Prompt 描述出来的行为，而是显式状态机**。七角色走 DAG、按状态迁移，失败有明确出口，因此断点续跑、定向返工、审计回溯都是代码能力而非模型自觉。

### 2.2 方案功能

| 能力 | 实现 | 对应赛事要求 |
|---|---|---|
| Agent 定义与配置 | 七角色角色卡 + 工具白名单 + 输入输出 schema | 五个核心模块之一 |
| 工作流编排 | DAG 构图 + 八状态机 + 并行层级 + 返工边 | 五个核心模块之一 |
| 任务调度与执行 | 多目标函数求解 + 硬约束过滤 + 事件驱动模拟器 | 五个核心模块之一 |
| 结果验证与监控 | 五层验证器（结构/约束/数值/交叉/语义）+ 运行轨迹 | 五个核心模块之一 |
| 反馈循环与优化 | rubric 评分 → 缺陷归因 → 定向返工 → 经验回写 | 五个核心模块之一 |
| 自我循环 | 执行—验证—修正闭环 + Plan-Do-Check-Act 双循环 | 硬性要求 |
| 工具集成 | MCP 式工具契约 + 越权拒绝 + 审计日志 | 鼓励项 |

### 2.3 技术内容

- **语言与依赖**：Python 3.10+，运行时零第三方依赖；知识包 YAML 解析用 PyYAML（安装脚本自动处理）。
- **模型接入**：`ModelGateway` 统一走国产模型的 OpenAI 兼容接口（DeepSeek / 智谱 GLM / 阿里 Qwen / 火山 Doubao / 百度千帆 / MiniMax），支持主模型与轻量模型两级路由（`GCS_LLM_LITE_MODEL`），未配置时自动回落；无 Key 或预算耗尽时降级为确定性模板，保证离线可复现。
- **数据**：`gcs/simulator.py` 事件驱动算力模拟器（L0），可注入故障、可版本化、指标可复算；领域知识包 `knowledge/ningxia_cluster.yaml`（版本 nx-2026.12，带指纹校验）。
- **评测**：`evaluation/run_eval.py` 六组配置 × 3 种子 × 80 作业，产出 `results.csv` / `summary.json` / `eval_report.html`，指标与看板同源同批。
- **工程化**：109 个单元测试（`gcs/` 覆盖率 87%）、操作台静态 Token 分级鉴权（`GCS_AUTH_*`，仅标准库）、GitHub Actions 四矩阵 CI（Ubuntu 3.10-3.13 + Windows 3.13）、覆盖率门禁 70%、一键安装脚本（`install.py --check`）。

## 三、应用成效

### 3.1 情况总述

平台已在本地完整跑通端到端链路：从自然语言任务描述，到 DAG 编排、调度求解、执行模拟、五层验证、定向返工，最后产出可截图的看板与可复算的指标。**六组对照实验**（每组 3 个随机种子、每次 80 作业）结果如下：

| 组别 | 配置 | SLA 达成 | 预算达标 | 单位成本(元/GPU·h) | 绿电窗口占比 | 碳排(kg) | rubric |
|---|---|---|---|---|---|---|---|
| G-A | FCFS 规则调度（无 Agent 协作） | 100.0% | 96.2% | 2.854 | 31.9% | 94.51 | 70 |
| G-B | SJF + 约束优先 | 99.6% | 99.6% | 2.828 | 31.9% | 93.53 | 80 |
| G-C | 通用 Agent 直接调度（模拟） | 100.0% | 99.2% | 2.560 | 33.1% | 91.10 | 80 |
| **G-D** | **本方案** | **99.6%** | **100.0%** | **2.389** | **37.8%** | **82.80** | **90** |
| G-E1 | 消融：去掉自省闭环 | 98.3% | 100.0% | 2.360 | 40.1% | 80.85 | 70 |
| G-E2 | 消融：去掉绿电权重 | 100.0% | 100.0% | 2.330 | 34.8% | 84.67 | 100 |

**相对 G-A 基线**：单位成本 −16.3%，总碳排 −12.4%，绿电窗口占比 +5.9 个百分点，rubric +20 分，预算达标率 96.2%→100%；代价是 SLA 由 100% 降至 99.6%（−0.4 个百分点）。

### 3.2 具体应用案例（模拟场景，已标注）

**案例：宁夏枢纽某训练批次的绿电对齐排程**

- **输入**：60 个作业的自然语言描述（「下周一前出结果，尽量用绿电，预算不要超」）。
- **编排**：需求解析角色输出 SLA=周一 09:00、预算上限、绿电权重 0.35；DAG 生成 12 节点、8 个并行层级。
- **调度**：候选过滤后按 J 值取优，把 47 个可延迟作业对齐到 11:00-15:00 的风光高出力窗口。
- **验证与返工**：首轮 rubric 70 分，验证器指出 3 个作业的卡型不匹配与 1 处预算越界；定向返工仅重跑相关节点，**2 轮后 rubric 100 分**（单次 demo 运行结果，见 `gcs.demo --jobs 60 --seed 20261111` 的 `artifact.json`；与 3.1 节六组统计评测的 G-A 70 → G-D 90 属不同口径，不可互换）。
- **产出**：SLA 100%、单位成本 2.60 元/GPU·h、绿电占比 71.5%、碳排 55.1 kg、token 消耗 153。

> 说明：以上数据由 `gcs/simulator.py` 生成，属**模拟场景**，非真实生产数据；选此场景是因为真实生产数据涉密，而模拟器可版本化、可复现、可现场复算。

## 四、商业模式

> 定位说明：本项目为赛事阶段的开源作品，**当前未开展任何商业运营**。以下为团队对可持续路径的判断，不构成营收承诺。

### 4.1 推广模式

| 路径 | 做法 | 门槛 |
|---|---|---|
| 开源社区先行 | Apache-2.0 全量开源，以「零依赖 + 一条命令跑通」降低试用门槛；争取进入高校课程与实训清单 | 低 |
| 高校教学渗透 | 作为「Agent 系统工程」课程脚手架：七角色、DAG、五层验证器均有可运行样例 | 低 |
| 枢纽侧试点 | 以知识包替换的方式对接真实集群调度接口，先做「旁路建议」（只给排程建议、不接管调度） | 中 |
| 赛事与生态曝光 | 通过大赛宣传展示、产教融合对接获取首批试点单位 | 低 |

### 4.2 市场空间

- **需求侧**：全国八大枢纽、十大数据中心集群的运营方普遍面临「绿电消纳考核 + 成本考核 + SLA 考核」三重压力，调度优化是刚需而非锦上添花。
- **供给侧**：通用 Agent 框架（LangChain、Dify、AgentScope 等）不做垂直调度；传统调度器（Slurm、Kubernetes）不做多目标绿电优化。**「Agent 编排 + 领域调度」的交叉位置目前竞争者稀少。**
- **可量化价值**：以本次实验的 −16.3% 单位成本与 −12.4% 碳排为参照，一个万卡级集群的年化节省具备现实意义（该推算需按真实电价与负载重算，不作宣传口径）。

### 4.3 生态运作

1. **知识包生态**：调度知识与代码解耦，行业方只需提供电价、PUE、机型功耗等结构化数据即可复用引擎——知识包可版本化、可交易、可审计。
2. **验证器插件**：五层验证器为插件式，行业方按自身合规要求追加校验层，不必改核心。
3. **评测基准共建**：六组对照实验的配置与原始数据全部公开，欢迎第三方提交新基线（如真实 DeerFlow 运行结果）替换当前的「模拟对照」。
